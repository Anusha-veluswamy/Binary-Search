5 · Think about it

Why sorted? Click "Shuffle shelf" and search for a book that's definitely there. What goes wrong?
Show answer

Binary search throws away half the shelf based on arr[mid] < key. That's only safe if everything left of mid is smaller and everything right is bigger. On an unsorted shelf it can discard the half that holds the book.

How many checks? For 7 books the worst case is 3 checks. What about 15 books? 1,000? 1,000,000?
Show answer

15 → 4, 1,000 → 10, 1,000,000 → 20. Each check halves the range, so it's about ⌊log₂ n⌋ + 1 checks. That's O(log n).

Best case. Why does the original example find "Data Structures" in just 1 check?
Show answer

It sits at index 3, which is exactly (0 + 6) // 2, the first middle. Best case is O(1).

Why //? What would go wrong with (low + high) / 2?
Show answer

/ gives a float like 2.5, and list indices must be integers. // rounds down, so with an even-sized range mid picks the left of the two middle books.

When does it stop? If the book isn't there, how does the loop know to give up?
Show answer

Each miss moves low up or high down. Eventually low > high: the range is empty, the while condition is False, and the function returns -1.

Why mid + 1? Why not just low = mid?
Show answer

arr[mid] was already checked and isn't the key, so it can be excluded. Using low = mid can leave the range stuck at the same size forever (an infinite loop).

Capitals matter. Try "Wrong capitalization". Which direction does the search go, and why?
Show answer

Lowercase letters sort after all uppercase ones ("d" > "P"), so "data structures" looks bigger than every title. The search keeps moving right and runs off the end.

Linear vs binary. Search for "Python Programming" here and in the Linear Search Explorer. Compare.
Show answer

Linear checks all 7; binary needs only 3. The gap grows fast: for 1,000,000 books it's up to 1,000,000 vs 20. The trade-off is that binary search needs the data sorted first.
